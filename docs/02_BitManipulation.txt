Q1: Which implementation do you think is better?
    int check_bit(int num, int pos)
    {
        return num & (1U << pos);
    }

    int check_bit(int num, int pos)
    {
        return (num & (1U << pos)) != 0;
    }

Ans: My answer: Version B. It has a well-defined interface: it always returns a boolean-like value (0 or 1). 
    The caller doesn't need to know that bit 5 would return 32, bit 7 would return 128, and so on. 
    You'll see Version A a lot in embedded code because sometimes you want the mask back, not just a boolean. Many embedded codebases prefer it because it's shorter and directly expresses "is any masked bit set?"

Q2: Why does num & 1 determine odd/even?
Ans:
    In binary, every bit except the least significant bit (LSB) has an even weight (2, 4, 8, 16...). Only the LSB has a weight of 1. 
    Therefore, if the LSB is 0, the sum of all set bits is even. If the LSB is 1, an extra 1 is added to an even sum, making the number odd. 
    num & 1 isolates the LSB, so it tells us whether the number is odd or even.

Q3: 1<<31 . Is it safe?
Ans:
    1 is a signed int. Left-shifting a signed value into the sign bit causes undefined behavior according to the C standard.

Q4: Why embedded engineers prefer hex over binary?
Ans:
    Easier to read than long binary strings.
    Every hex digit represents exactly 4 bits.
    Datasheets and register maps use hexadecimal.
    Debuggers and memory windows display hexadecimal.

Q9:  For setting a bit in register? Suppose a register field starts at bit P and has width W.
    reg &= ~(MASK << POSITION);
    reg |= (VALUE << POSITION);

    reg &= ~(((1U << W) - 1U) << P);
    reg |= (value << P);
    That's why CMSIS drivers and vendor HALs often use formulas or macros instead of hardcoded numbers.
